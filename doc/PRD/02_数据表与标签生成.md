## 3. 瓶颈定义

结合调研文档，当前项目中建议把制造瓶颈定义为：

```text
在给定时间窗口内，限制系统吞吐、造成 WIP 堆积、资源长时间忙碌、上下游阻塞/饥饿传播，或导致订单完成延迟的关键资源、工位、物流路径或物料供应点。
```

该定义需要满足两个要求：

- 能从 Isaac Sim 仿真日志中观测；
- 能进一步转换成监督学习或事件预测标签。

## 4. 瓶颈维度体系

当前第二部分建议采用三层瓶颈维度：

```text
Queue State
Process State
System State
```

### 4.1 Queue State

Queue State 用于描述 WIP 堆积、等待和 buffer 占用。

核心指标：

```text
queue_length_s
avg_waiting_time_s
occupancy_ratio_s
queue_growth_rate_s
full_duration_ratio_s
```

主要来源：

```text
buffer_event_log.csv
job_trace.csv
episode_config.csv
```

适用对象：

```text
buffer
machine input buffer
station waiting area
```

### 4.2 Process State

Process State 用于描述资源自身是否长期处于加工、等待、阻塞、饥饿、故障或维修状态。

核心指标：

```text
active_pct_s
current_active_duration_s
blocked_time_s
starved_time_s
processing_time_s
inter_departure_var_s
```

后续增强指标：

```text
setup_time_s
down_time_s
repair_time_s
tool_change_time_s
```

主要来源：

```text
resource_event_log.jsonl
job_trace.csv
disturbance_log.csv
```

适用对象：

```text
machine
gantry
human
transport_robot
```

### 4.3 System State

System State 用于描述瓶颈对上下游和系统吞吐的传播影响。

核心指标：

```text
upstream_blocked_ratio_s
downstream_starved_ratio_s
route_delay_s
material_shortage_propagation_s
throughput_rolling_s
throughput_loss_s
affected_nodes_s
```

主要来源：

```text
resource_event_log.jsonl
buffer_event_log.csv
route_transport_task.csv
material_inventory_log.csv
job_trace.csv
```

适用对象：

```text
machine
buffer
route
material
system
```

### 6.1 主模型导向的数据分层

第三部分主模型确定为动态图事件预测后，Queue / Process / System 三类瓶颈维度仍然保留，但它们不再作为三张互相独立的数据表，而是被整理为：

```text
Queue State   -> node features
Process State -> node features
System State  -> edge features + global features + label explanation
```

因此，第二部分的数据表设计应分为三层：

```text
P0 主模型输入：
  当前 raw logs 可以稳定派生的 node / edge / global features

P0 标签生成：
  bottleneck_score、bottleneck_node、bottleneck_type、duration、severity_weak

P1/P2 增强：
  agent action、路径拥堵、故障维修状态、视觉特征、反事实吞吐损失
```

这样可以避免把所有调研指标都写成第一版必须实现。

## 8. 标签生成设计

### 8.1 bottleneck_score

第一版可以先使用调研文档中的综合分数法：

```text
bottleneck_score_s(t) =
    0.25 * norm(queue_length_s)
  + 0.20 * norm(avg_waiting_time_s)
  + 0.25 * active_pct_s
  + 0.10 * norm(current_active_duration_s)
  + 0.10 * upstream_blocked_ratio_s
  + 0.10 * downstream_starved_ratio_s
```

为了适配当前代码，建议第一版把资源分为三类计算：

```text
machine / gantry / human / transport_robot：重 Process State
buffer：重 Queue State
material：重 shortage 和 propagation
```

如果所有资源共用同一 score，需要对不适用字段填 0，并额外记录 `resource_type`。

### 8.2 bottleneck_label.csv

建议粒度：

### 8.3 瓶颈表现类型与归因类型

为了避免把“瓶颈表现”和“瓶颈原因”混成一个字段，第一版标签建议拆成两个 type：

```text
bottleneck_symptom_type：瓶颈表现类型
bottleneck_cause_type：瓶颈归因类型
```

`bottleneck_symptom_type` 用 Queue / Process / System 三类维度判断，表示瓶颈在数据上表现为什么：

```text
QUEUE_ACCUMULATION
RESOURCE_BUSY
STARVATION
BLOCKAGE
SYSTEM_THROUGHPUT_DROP
UNKNOWN
```

`bottleneck_cause_type` 用物料、运输、上下游状态和 agent 调度动作推断，表示瓶颈可能由什么机制导致：

```text
PROCESS_CAPACITY_LIMIT
MATERIAL_SHORTAGE
TRANSPORT_DELAY
AGENT_ALLOCATION
DOWNSTREAM_BLOCKAGE
DISTURBANCE
UNKNOWN
```

第一版没有真实因果标注时，`bottleneck_cause_type` 应作为弱标签生成，并通过 `cause_label_confidence` 标记置信度。

建议弱归因规则优先级：

```text
if disturbance_log 有明确扰动覆盖当前窗口:
    bottleneck_cause_type = DISTURBANCE
    cause_label_confidence = high

elif material_shortage_flag_s == 1 or material_shortage_duration_s > threshold:
    bottleneck_cause_type = MATERIAL_SHORTAGE
    cause_label_confidence = medium

elif route_delay_s 高 and starved_ratio_s 高:
    bottleneck_cause_type = TRANSPORT_DELAY
    cause_label_confidence = medium

elif downstream buffer 满 or blocked_ratio_s 高:
    bottleneck_cause_type = DOWNSTREAM_BLOCKAGE
    cause_label_confidence = medium

elif resource idle 但任务 waiting，或 agent_action_count_s / allocation_change_count 异常高:
    bottleneck_cause_type = AGENT_ALLOCATION
    cause_label_confidence = low_or_medium

elif active_pct_s 高 and queue_growth_rate_s 高:
    bottleneck_cause_type = PROCESS_CAPACITY_LIMIT
    cause_label_confidence = medium

else:
    bottleneck_cause_type = UNKNOWN
    cause_label_confidence = low
```

水喉产线示例：

```text
MIG焊面前 queue_length 持续增长
MIG焊面 active_pct 高
下游涂漆防锈未阻塞
route_delay 不高
material_shortage_flag = 0

=> bottleneck_symptom_type = QUEUE_ACCUMULATION
=> bottleneck_cause_type = PROCESS_CAPACITY_LIMIT
```

另一个示例：

```text
配料点焊 waiting_time 高
human 或 robot 存在 idle
但 Agent D 没有稳定分配到配料点焊任务
后续氩弧焊底焊 starved

=> bottleneck_symptom_type = STARVATION 或 QUEUE_ACCUMULATION
=> bottleneck_cause_type = AGENT_ALLOCATION
```

注意：`PROCESS_CAPACITY_LIMIT` 不应作为默认先验原因，而应在排除物料、运输、下游阻塞和明显调度异常后再使用。这样可以减少把动态调度问题误判为工序能力不足。

## 9. 当前不合理或需要澄清之处

### 9.1 `waiting_* -> BLOCKED` 的状态映射存在语义风险

当前 `map_machine_state()` 中：

```text
waiting_{task} -> BLOCKED
reason = downstream_not_ready
```

这个映射需要重新确认。

从当前任务推进逻辑看，`waiting_*` 很可能表示机器工位被预留、物料正在前往或等待任务推进，并不一定表示“下游 buffer 满导致无法输出”。这更接近：

```text
WAITING_FOR_MATERIAL
READY_RESERVED
STARVED
```

如果继续把 `waiting_*` 作为 `BLOCKED`，后续 `blocked_time_s` 会被高估，System State 的上下游传播方向也可能被算反。

建议后续修正为：

```text
waiting_{task} -> STARVED 或 WAITING_FOR_MATERIAL
materialReadyFor_{task} -> READY 或 WAITING_TO_PROCESS
真正 BLOCKED 只在“下游 buffer 满/无法释放产品”时触发
```

### 9.2 当前状态体系比调研九态更粗

调研中提到的九类细粒度状态包括：

```text
Producing
Set up
Tool change
Repair
Breakdown
Waiting for repair
Stop
Blockage
Starvation
```

当前代码实际归一化状态主要是：

```text
IDLE
PROCESSING
WAITING
BLOCKED
STARVED
STOP
```

其中 `DOWN`、`REPAIR`、`SETUP`、`TOOL_CHANGE` 当前没有完整状态机和扰动注入支持。

因此，文档中不能把 `down_time_s`、`repair_time_s`、`setup_time_s` 写成当前已可稳定采集，只能写成后续扩展指标。

### 9.3 `disturbance_log.csv` 目前只有表结构

当前代码会创建 `disturbance_log.csv` 表头，但没有完整的扰动注入和恢复机制。

因此：

- 当前不能直接得到可靠的 root cause 真值；
- `machine_failure`、`human_unavailable`、`transport_delay`、`material_shortage` 等原因标签需要后续补扰动模块；
- 第一版 root cause 可以先用规则推断，但应标记为弱标签。

### 9.4 `material_inventory_log.csv` 目前更像位置与可用性日志

当前 `material_inventory_log.csv` 的 `inventory_level` 是基于 submaterial 是否在某个 storage/location 中得到的 0/1 标记。

这适合当前水喉工艺的件级物料跟踪，但还不是严格意义上的库存系统。

后续如果要支持真实物料瓶颈，应扩展：

```text
批量库存
补料计划
安全库存
供应延迟
消耗速率
物料到达事件
```

### 9.5 `route_transport_task.csv` 还不能完整表达路径拥堵

当前物流表可以记录物流任务生命周期，但 `route_id` 目前为空，路径边占用、交叉口等待、路线拥堵还没有显式记录。

因此，当前可以分析“物流任务等待/延迟”，但还不能严谨地区分：

```text
机器人不足
龙门架不足
路径拥堵
路线冲突
搬运距离过长
```

### 9.6 `episode_config.csv` 中 arrival_rate 为空

当前订单主要来自固定配置，`product_mix` 也基本等同于 `product_order`。

如果后续要做订单到达率、负载强度和多产品混流对瓶颈的影响，需要补充随机订单生成机制，或在离线阶段根据 job 创建时间反算 arrival rate。

### 9.7 事件驱动日志需要离线补齐时间区间

`resource_event_log.jsonl` 是状态变化事件，不是每一步全量快照。

这本身是合理的，但窗口聚合时必须根据相邻事件补齐状态持续区间，否则无法正确计算：

```text
active_pct_s
blocked_time_s
starved_time_s
current_active_duration_s
```

另外，当前默认 `log_resource_init_events=False`，离线聚合脚本需要从 episode reset 初始状态补齐每个资源的初始状态。

### 9.8 部分指标存在重复，需要按用途取舍

主模型输入不宜把所有高度相关字段无差别塞入。

第一版建议：

```text
模型输入优先使用：
  blocked_ratio_s
  starved_ratio_s
  active_pct_s
  occupancy_ratio_s

标签解释 / severity 保留：
  blocked_time_s
  starved_time_s
  active_time_s
  duration_s
```

典型重复关系：

```text
blocked_time_s 与 blocked_ratio_s
starved_time_s 与 starved_ratio_s
processing_time_s 与 active_pct_s
queue_length_s 与 occupancy_ratio_s
material_shortage_flag_s 与 material_shortage_duration_s
throughput_rolling 与 output_rate_s
```

第一版不要求手动删除所有重复特征，但需要在实验中通过 ablation、feature importance 或相关性分析确认是否保留。

验收标准：

- 能对一个完整 run 生成窗口表；
- 支持 `window_size` 和 `stride` 参数；
- 输出包含 machine、gantry、human、transport_robot、buffer、material 节点。

### P0：实现第一版 bottleneck_label

基于窗口特征生成：

```text
bottleneck_label.csv
bottleneck_event.csv
```

第一版可以使用 score + threshold + min_duration 规则。

验收标准：

- 每个窗口有 `bottleneck_node` 和 `bottleneck_score`；
- 连续高分窗口可以合并成事件；
- 每个标签文件记录 `label_version` 和 `score_config`。

### P1：修正资源状态映射

优先修正或澄清以下映射：

```text
waiting_* 是否应为 BLOCKED
materialReadyFor_* 是否应为 READY
human/robot wait 是否应统一为 STARVED
```

验收标准：

- 每个状态都有明确触发条件；
- `BLOCKED` 只表示无法向下游释放或下游不可接收；
- `STARVED` 只表示上游无物料/无任务/等待伙伴导致无法工作。

### P1：补充 agent_action_log 或动作派生表

虽然第二部分主要是数据表和标签，但多智能体调度动作会影响瓶颈形成，因此建议补充：

```text
agent_action_log.csv
```

或先离线派生：

```text
agent_action_derived.csv
```

字段应按当前 A/B/C/D 智能体结构设计，而不是订单/设备/运输/人员四类资源智能体。

### P1：补充扰动注入和 root cause 真值

为了让瓶颈标签具有因果解释，后续应补充扰动模块。

最低支持：

```text
machine_slowdown
machine_failure
human_unavailable
transport_delay
material_shortage
buffer_capacity_limit
```

验收标准：

- 扰动开始和恢复都写入 `disturbance_log.csv`；
- 标签生成时优先使用扰动作为 root cause；
- 无扰动场景下 root cause 使用规则推断并标记为弱标签。

### P2：补充路径级和图结构数据

后续如果要做 GNN 或动态图预测，需要进一步补充：

```text
process_flow_edge
transport_route_edge
material_supply_edge
route_occupancy
edge_delay
edge_conflict_count
```

第一版可以先从工艺配置和 task_record 中离线建静态图，后续再补动态路径边。

## 12. 由预测模型设计反推的补充要求

第三部分预测模型确定采用“图序列输入 + 多任务事件标签”后，第二部分的数据表与标签需要进一步明确以下要求。

### 12.1 窗口特征表必须服务于图节点

`window_feature_table.csv` 不能只做全局统计，必须保留节点粒度：

```text
run_id
env_id
episode_id
window_id
resource_id
resource_type
```

这样后续才能构建：

```text
X_t: node feature matrix
A_t: graph adjacency
U_t: global feature vector
```

### 12.2 标签必须同时支持窗口级和事件级

预测模型需要两层标签：

```text
bottleneck_label.csv：窗口级标签，用于训练分类/回归 head
bottleneck_event.csv：事件级标签，用于合并连续窗口和评估事件预测
```

每个标签文件必须记录：

```text
label_version
score_config
threshold
min_duration
prediction_horizon
```

避免后续实验无法复现标签定义。

### 12.3 特征必须避免未来信息泄漏

以下字段只能使用当前窗口或历史窗口信息：

```text
disturbance_flag
throughput_rolling
agent_action_count
route_delay
material_shortage_flag
```

以下字段不能作为当前输入直接使用，只能作为标签或评估指标：

```text
future_bottleneck_node
future_bottleneck_symptom_type
future_bottleneck_cause_type
future throughput_loss
future disturbance
future completion count
```

### 12.4 route 第一版作为边特征

由于当前 `route_transport_task.csv` 尚未完整记录 `route_id`、路径占用和路径冲突，第一版不建议把 route 作为独立节点。

第一版建议：

```text
route_transport_task.csv -> transport_edge feature
```

后续当路径级数据补齐后，再升级为：

```text
route node
route segment node
intersection node
```

### 12.5 severity 第一版用弱定义

在没有无扰动 baseline 和反事实仿真前，`severity` 不建议直接写成真实吞吐损失。

第一版建议：

```text
severity = f(bottleneck_score, duration, affected_nodes)
```

后续补充 baseline 仿真后，再升级为：

```text
severity = throughput_loss_vs_baseline
```
