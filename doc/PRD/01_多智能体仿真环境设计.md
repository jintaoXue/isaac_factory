# PRD 01：多智能体仿真环境设计

## 1. 文档目的

本文档用于沉淀“多智能体仿真环境设计”这一部分的当前代码状态与后续扩展方向。

当前代码基础已经具备 Isaac Sim / Isaac Lab 工厂仿真环境、规则策略与 MARL 策略入口、多智能体串行决策接口、资源管理器、任务调度逻辑、物理仿真推进和瓶颈数据采集基础。因此，第一部分不应被描述为从零建设的设想，而应描述为：

- 现有仿真平台已经实现的能力；
- 当前多智能体机制在代码中的真实形态；
- 与论文/方案中更完整的“订单-设备-运输-人员”智能体设想之间的差距；
- 后续为了瓶颈预测、数据增强和反馈控制需要补齐的扩展点。

## 2. 范围边界

本 PRD 只覆盖“多智能体仿真环境设计”，重点是仿真平台、智能体调度链路、环境状态推进和数据生成基础。

本文档不展开以下内容：

- 瓶颈预测模型结构；
- 时窗特征工程；
- GNN / Transformer 等预测模型训练；
- 瓶颈标签定义的完整实验设计；
- 论文实验章节。

这些内容应在后续 PRD 或完整方案文档中单独展开。

## 3. 当前代码状态

### 3.1 仿真平台入口

当前仿真任务通过 `train.py` 启动，训练/仿真任务名为 `HRTPaHC-v1`。

环境注册位置：

```text
source/isaaclab_tasks/isaaclab_tasks/direct/hc_factory/__init__.py
```

核心环境入口类：

```text
isaaclab_tasks.direct.hc_factory.envs.hc_env:HcVectorEnv
```

当前环境基于 Isaac Lab 的 `DirectRLEnv` 构建，支持通过 Gym 注册任务，并根据算法参数选择 `rule_based` 或 `marl` 两类策略入口。

### 3.2 向量化仿真结构

当前环境不是单一工位仿真，而是向量化环境结构。

核心层级如下：

```text
HcVectorEnv
  -> HcVectorEnvBase
    -> HcSingleEnv × num_envs
    -> RouteManagerVectorEnv
    -> Isaac Sim scene / physics
    -> Bottleneck run context
```

其中：

- `HcVectorEnv`：对外提供强化学习环境接口；
- `HcVectorEnvBase`：管理多个单环境、场景加载、仿真步进和数据写回；
- `HcSingleEnv`：承载单个工厂环境内的订单、物料、设备、人、机器人和任务逻辑；
- `RouteManagerVectorEnv`：负责路径、运输和移动相关逻辑；
- Isaac Sim / Isaac Lab：负责 USD 场景、刚体、关节、物理推进和渲染。

### 3.3 单环境管理器组成

当前每个 `HcSingleEnv` 内部已经注册多个管理器，用于模拟制造系统中的关键对象和流程。

主要管理器包括：

```text
StorageManager
ProductMaterialManager
MachineManager
HumanManager
RobotManager
CameraManager
PerceptionManager
BottleneckDataCollector
AlgoMultiAgentMasker
TaskManager
```

这些管理器共同完成以下工作：

- 订单与产品物料状态维护；
- 机器设备状态维护；
- 人员与机器人资源状态维护；
- 工艺任务与物流任务派发；
- 运输路径与位置状态更新；
- 视觉/感知数据采集；
- 瓶颈相关原始日志采集；
- 多智能体动作可行性 mask 计算。

### 3.4 环境 step 流程

当前每一步仿真大致按以下流程推进：

```text
外部策略输出 action
  -> HcVectorEnv.step()
  -> HcVectorEnvBase.step_env_logic()
  -> HcSingleEnv.step_env_logic()
  -> 各类 manager 更新逻辑状态
  -> TaskManager 解析动作并生成任务记录
  -> AlgoMultiAgentMasker 更新下一步动作 mask
  -> PerceptionManager / BottleneckDataCollector 采集数据
  -> HcVectorEnvBase.step_env_physics()
  -> apply_data_to_sim()
  -> sim.step()
```

这说明当前仿真平台已经具备“策略决策-任务调度-资源状态变化-物理仿真推进-数据采集”的闭环。

## 4. 当前多智能体机制

### 4.1 当前并不是四类独立资源智能体

方案中常见的表达是：

```text
订单智能体
设备智能体
运输智能体
人员智能体
```

但当前代码中的真实多智能体结构不是这四类独立资源智能体，而是围绕产品制造决策形成的四层串行决策链。

当前四个智能体分别是：

```text
Agent A: ProductSequencingAgent
Agent B: ProductSelectionAgent
Agent C: ProcessTaskPlanningAgent
Agent D: HumanRobotMachineAllocationAgent
```

### 4.2 当前决策链含义

当前多智能体动作可以理解为：

```text
A：决定产品类型/生产序列
B：在候选产品中选择当前要推进的产品
C：为该产品选择下一道工艺任务或物流任务
D：为任务分配人、机器人、机器等执行资源
```

该设计更接近“层级式任务调度智能体”，而不是完全分散自治的资源智能体。

### 4.3 当前策略类型

当前代码中已支持两类策略：

- `rule_based`：基于规则的多智能体调度；
- `marl`：基于 DQN 的多智能体强化学习调度。

其中 MARL 版本仍沿用 A/B/C/D 四层动作结构，并通过 mask 限制不可行动作。

### 4.4 当前 mask 机制

当前 `AlgoMultiAgentMasker` 会根据以下信息生成动作 mask：

- 人员是否可用；
- 机器人是否可用；
- 设备是否可用；
- 物料是否满足任务要求；
- 产品当前工艺进度是否允许执行下一任务。

因此，Agent C 和 Agent D 的可行动作并不是任意选择，而是受到工艺路线、资源状态和物料状态共同约束。

## 5. 当前工艺与制造流程覆盖

当前代码中的主产品工艺是 `ProductWaterPipe`，与“水喉/钢管加工”工艺路线相对应。

当前流程可以概括为：

```text
钢管
  -> 切管下料
  -> 管口压槽
  -> 配料点焊
  -> 氩弧焊底焊
  -> MIG焊面焊
  -> 涂漆防锈
  -> 成品
```

在代码中，这些加工任务与物流任务穿插出现。每道加工任务前通常存在对应的物流任务，用于将物料移动到目标工位。

主要工艺任务包括：

```text
pipe_cutting
pipe_grooving
batch_spot_welding
arc_welding_root
MIG_welding_surface
paint_rust_proof
```

该部分说明当前平台已经具备一个可用于瓶颈研究的完整制造流程，而不是只有抽象队列或简化排产模型。

## 6. 当前数据生成能力

当前瓶颈数据采集已经在代码中实现基础版本，主要由 `BottleneckDataCollector` 完成。

当前已生成或支持的原始日志包括：

```text
run_manifest.json
episode_config.csv
disturbance_log.csv
resource_event_log.jsonl
job_trace.csv
buffer_event_log.csv
route_transport_task.csv
material_inventory_log.csv
```

这些日志可以支持后续构建：

- 资源状态时间线；
- 订单/产品加工轨迹；
- 工位缓冲区状态；
- 物流运输任务记录；
- 物料库存状态；
- episode 级别仿真配置；
- 后续扰动事件记录。

需要注意的是，当前还没有完整实现用于模型训练的最终特征表和标签表，例如：

## 7. 当前限制与差距

### 7.1 智能体结构差距

当前代码中的智能体是 A/B/C/D 层级调度链，不是完全独立的订单、设备、运输、人员智能体。

如果后续论文或系统方案要使用“订单-设备-运输-人员”四类智能体表达，需要明确这是后续扩展设计，而不是当前已完成代码状态。

### 7.2 订单生成能力差距

当前代码以配置化订单数量和产品类型为主，尚未形成完整的随机订单到达机制。

后续可以扩展：

- 订单随机到达；
- 多产品混流；
- 交期约束；
- 优先级订单；
- 加急订单；
- 订单取消或返工。

### 7.3 扰动机制差距

当前数据采集中已经预留 `disturbance_log.csv`，但完整扰动注入机制尚未形成。

后续可以扩展：

- 设备故障；
- 人员缺勤；
- 机器人占用或异常；
- 物流路径拥堵；
- 物料短缺；
- 工艺时间波动；
- 返工与质量异常。

### 7.4 预测反馈差距

当前平台已经可以生成瓶颈相关原始数据，但还没有把预测模型结果反馈给调度智能体。

后续可以扩展为：

```text
仿真运行
  -> 数据采集
  -> 时窗特征构造
  -> 瓶颈预测模型
  -> 调度策略调整
  -> 新一轮仿真
```

这会形成真正的“瓶颈预测-调度反馈”闭环。

## 8. 后续扩展需求

### P0：保持当前仿真平台可运行

必须保证现有 `HRTPaHC-v1` 任务、`rule_based` 策略和水喉工艺流程能够稳定运行。

验收标准：

```bash
python train.py --task HRTPaHC-v1 --algo rule_based --num_envs 1 --headless
```

运行后应能正常推进 episode，并生成基础仿真日志。

### P0：明确当前 A/B/C/D 多智能体接口

文档、代码注释和后续方案中应统一说明：

```text
当前实现 = A/B/C/D 层级式多智能体调度链
未来扩展 = 订单/设备/运输/人员资源级智能体
```

避免把尚未实现的资源级智能体误写成当前代码能力。

### P1：补充智能体动作日志

建议新增或派生 `agent_action_log.csv`，记录每一步 A/B/C/D 智能体决策。

建议字段包括：

```text
episode_id
env_id
time_step
agent_A_action
agent_B_action
agent_C_action
agent_D_action
selected_product
selected_task
selected_human
selected_robot
selected_machine
valid_mask_summary
policy_type
```

该日志可以帮助解释“多智能体如何调度仿真生成数据”。

### P1：补充场景配置层

建议把以下变量整理为可配置实验场景：

```text
订单数量
产品类型组合
设备数量
人员数量
机器人数量
工艺时间分布
物流路径参数
物料初始库存
episode 时长
随机种子
```

这样后续可以系统生成不同瓶颈场景。

### P1：补充扰动注入机制

建议在现有 `disturbance_log.csv` 基础上补齐扰动注入模块。

扰动模块至少应支持：

```text
扰动类型
扰动开始时间
扰动持续时间
影响对象
影响强度
恢复时间
是否可被智能体观测
```

### P2：扩展资源级智能体

如论文或系统需要更强的“多智能体自治”表达，可在当前 A/B/C/D 调度链基础上逐步扩展资源级智能体：

```text
OrderAgent
MachineAgent
TransportAgent
HumanAgent
```

建议不要直接替换当前 A/B/C/D 结构，而是先做兼容式扩展：

```text
A/B/C/D 负责任务级调度
资源级 Agent 负责局部状态评估、可用性反馈和扰动响应
```

### P2：接入瓶颈预测反馈

后续可将瓶颈预测模型输出作为调度策略输入。

可扩展字段包括：

```text
predicted_bottleneck_resource
predicted_bottleneck_type
prediction_confidence
recommended_action
policy_adjustment
```

最终目标是让仿真系统从“数据生成平台”扩展为“预测辅助调度平台”。

## 10. 阶段性结论

第一部分当前状态可以总结为：

```text
已有：Isaac Sim / Isaac Lab 工厂仿真平台
已有：水喉制造流程
已有：A/B/C/D 多智能体调度链
已有：规则策略与 MARL 策略入口
已有：资源管理器、任务管理器、路径管理器
已有：瓶颈数据采集基础日志

待扩展：资源级智能体
待扩展：随机订单与多产品混流
待扩展：扰动注入机制
待扩展：智能体动作日志
待扩展：时窗特征与瓶颈标签
待扩展：预测结果反馈调度
```

因此，论文或项目文档中关于“多智能体仿真环境设计”的表述应以当前代码为基础：先描述已经存在的 Isaac Lab 多智能体制造仿真平台，再把订单、设备、运输、人员智能体和预测反馈机制作为下一阶段扩展。

## 11. 由预测模型设计反推的补充要求

第三部分预测模型确定采用“动态图时序预测 + 事件预测头”后，第一部分需要补充以下仿真平台约束：

```text
resource_id 必须稳定
job_id / task_id 必须稳定
process topology 必须能离线导出
policy_type 必须记录
scenario_id 后续需要记录
A/B/C/D agent 决策链需要保留
agent_action_log 或 agent_action_derived 后续需要补齐
预测结果反馈调度接口后续需要预留
```

也就是说，后续扩展资源级智能体时，不应破坏当前 A/B/C/D 调度链与 task_record 的可追踪性。预测模型需要从这些记录中恢复动态图关系，例如某个窗口内哪个产品被选择、哪个任务被派发、哪个 human / robot / machine 被绑定。

第一版模型不要求仿真环境实时调用预测模型；预测闭环可以放在 P2。当前更重要的是保证仿真输出的数据能稳定重建：

```text
工艺图
物流图
物料供应图
agent 动态调度图
```

### 11.1 主模型导向的仿真扩展优先级

为了避免仿真平台过早承担过多模型需求，第一版只要求稳定支持主模型最小数据闭环。

P0 必须保持或补齐：

```text
稳定 resource_id / job_id / task_id
稳定 ProductWaterPipe 工艺拓扑
policy_type 写入 episode_config
resource_event_log / job_trace / buffer_event_log / route_transport_task / material_inventory_log 稳定输出
route 第一版作为 transport edge，不作为独立 route node
```

P1 再补：

```text
scenario_id
agent_action_log 或 agent_action_derived
随机订单 / 多产品 mix
扰动注入和恢复记录
路径级 route_id / route_delay 更完整记录
```

P2 再补：

```text
DOWN / REPAIR / SETUP / TOOL_CHANGE 状态机
route node / route segment node / intersection node
视觉低层运动特征
throughput_loss_vs_baseline 反事实实验
预测结果实时反馈调度
```

这样第一部分与第三部分保持一致：当前仿真环境先作为可控数据生成与原始日志平台，后续再逐步扩展为动态预测反馈系统。
