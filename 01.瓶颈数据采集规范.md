## 1. 总体流程

```text
Isaac Sim 仿真（rule_based 主循环，逻辑不变）
    ↓
HcSingleEnvBase.step_env_logic 末尾
    ↓ BottleneckDataCollector（新增，只读 env_state_action_dict）
原始日志 7 表（output/bottleneck_dataset/<run_id>/episode_XX/env_YY/）
    ↓ 离线 python3 -m bn_agg
derived/episode_XX/env_YY/{window_feature_table,bottleneck_label,bottleneck_event,job_kpi}.csv
    ↓ PDFormer factory_bn.export_dataset
GNN / 点过程训练输入
```

采集原则（与调研文档一致）：

1. **事件驱动优先**：`resource_event_log`、`buffer_event_log` 在状态变化时写入；`job_trace`、`route_transport_task` 在任务边界写入。
2. **不改业务逻辑**：不修改 `TaskManager`、四层 Agent、物理步。
3. **时间统一**：所有表记录 `time_step`（整数逻辑步）和 `logic_time_s`（`time_step × logic_dt`，默认 `logic_dt=1.0` 秒）。`resource_event_log` 额外保留 `sim_time_s`（物理仿真时间）供对照。
4. **资源 ID 稳定**：同一物理对象在整个 run 内 `resource_id` 不变，便于窗口聚合与 GNN 建图。

## 2. 时间与 ID 约定



### 2.1 时间字段


| 字段             | 类型    | 计算方式                                 | 说明                                                            |
| -------------- | ----- | ------------------------------------ | ------------------------------------------------------------- |
| `time_step`    | int   | `env["time_step"]`                   | 环境逻辑步计数，与 `processing_time`、subtask 计时同单位                     |
| `logic_time_s` | float | `time_step × logic_dt`               | 默认 `logic_dt = 1.0`，与工序/子任务时长同量纲                              |
| `sim_time_s`   | float | `time_step × sim.dt`                 | 仅 `resource_event_log`；默认 `sim.dt = 1/120`                    |
| `run_id`       | str   | 启动时生成，如 `2026-07-06_12-00-00_seed42` | 一次 `train.py` 运行唯一标识                                          |
| `episode_id`   | int   | 从 0 递增；每次 `reset_env` +1             | `rule_based` 用 `--max_sim_episodes` 停采集（同时设 `--max_episodes`） |
| `env_id`       | int   | `HcSingleEnv.env_id`                 | 向量化环境索引                                                       |


窗口聚合阶段以 `logic_time_s` 对齐到 30s / 60s 窗口（脚本默认；也可加 10s）。

### 2.2 job_id 约定


| 字段             | 取值                                                          |
| -------------- | ----------------------------------------------------------- |
| `job_id`       | `product_index`（`task_record["product_index"]`）             |
| `product_type` | `task_record["product"]`，如 `ProductWaterPipe`               |
| `task_id`      | `f"{product_index}_{task}"`，如 `3_logistic_for_pipe_cutting` |


同一 `job_id` 在不同工序段用 `station_id` + `task` 区分多行 `job_trace`。

## 3. 资源 ID 命名规范

GNN 节点与 `resource_event_log.resource_id` 使用下表命名（**第一版定稿后不要改**）：


| resource_type     | resource_id 格式                         | 示例                                                       |
| ----------------- | -------------------------------------- | -------------------------------------------------------- |
| `machine`         | `{machine_type}_ws{workstation_idx}`   | `num02_rollerbedCNCPipeIntersectionCuttingMachine_ws0`   |
| `gantry`          | `gantry_{gantry_idx}`                  | `gantry_0`                                               |
| `human`           | `human_{idx}`                          | `human_0`（对应 `num_00_NormalHuman` 等 key 中的 idx）          |
| `transport_robot` | `robot_{idx}`                          | `robot_0`                                                |
| `buffer`          | `storage_{class_name}_{idx:02d}`       | `storage_BlackStorage_00`                                |
| `material`        | `material_{job_id}_{submaterial_name}` | `material_0_product_00_pipe_raw`（按 job + submaterial 粒度） |
| `job`             | `job_{product_index}`                  | `job_3`                                                  |


`station_id`（用于 `job_trace`）与 machine 节点对齐：

- 加工工位：`station_id = resource_id`（machine 格式）
- 物流段：`station_id = logistic_{task}` 或 `gantry_{idx}`

## 4. 状态映射表（代码 → 文档九态）

仿真原始状态在 `env_state_action_dict` 中为字符串；写入 `resource_event_log` 前映射为调研文档中的**统一状态名**。

### 4.1 Machine 工位（`env["machine"][type]["state"][ws_idx]`）


| 代码 state                  | 映射状态         | reason 建议                                |
| ------------------------- | ------------ | ---------------------------------------- |
| `free`                    | `IDLE`       | —                                        |
| `working_{task}`          | `PROCESSING` | `task={task}`                            |
| `waiting_{task}`          | `BLOCKED`    | 下游未就绪，物料等待加工或输出                          |
| `materialReadyFor_{task}` | `WAITING`    | 物料到位，等待开工                                |
| `invalid`                 | `STOP`       | 未启用工位；**L0 关掉的双工位 ws1**；或 **L2 机台故障**（注入器把空闲工位置 `invalid`） |


没有单独的 `DOWN` / `REPAIR` 字符串。L2 故障在 `resource_event_log` 里表现为 `to_state=STOP`（`raw_to_state=invalid`，`reason=invalid_workstation`），并在 `disturbance_log` 写 `machine_failure`。

### 4.2 Gantry（`env["machine"]["num07_gantry_group"]`）


| 代码 state         | 映射状态         | reason                                                          |
| ---------------- | ------------ | --------------------------------------------------------------- |
| `free`           | `IDLE`       | —                                                               |
| `working_{task}` | `PROCESSING` | 龙门架执行物流                                                         |
| `invalid`        | `STOP`       | 未启用，或 L2 物流扰动把龙门置 `invalid`（`disturbance_type=transport_delay`） |


subtask 为 `finding_free_gantry` 且未完成时，对**等待龙门架的 job** 记 transport waiting（见 `route_transport_task.delay_reason`），不单独给 gantry 写 `STARVED`。

### 4.3 Human（`env["human"][key]["state"]`）


| 代码 state                     | 映射状态         | reason                         |
| ---------------------------- | ------------ | ------------------------------ |
| `free`                       | `IDLE`       | —                              |
| `working_disturbance_absent` | `PROCESSING` | L2 人员离岗；无 task 时仍记 `working_*` |
| `working_{task}`             | `PROCESSING` | 结合 `subtask_name` 细分           |


结合 `ongoing_task_record` 的 subtask 行（`subtasks_dict["ongoing"][0]`）：


| subtask_name                                                      | 映射状态             | reason                                                                          |
| ----------------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------- |
| `go_to_material` / `go_to_goal_area` / `go_to_processing_machine` | `PROCESSING`（移动） | `subtask=walk`；`CfgSubtaskPredefinedTimeGallery` 里这三项为 `None`（等到路径走完，不是固定 10 步） |
| `control_machine` / `control_gantry` 等                            | `PROCESSING`     | `subtask=operate`                                                               |
| `wait`                                                            | `STARVED`        | `waiting_for_gantry_or_partner`                                                 |
| （无 ongoing_task）且 state=free                                      | `IDLE`           | —                                                                               |




### 4.4 Robot（`env["robot"][key]["state"]`）

与 Human 类似：`free` → `IDLE`，`working_{task}` → `PROCESSING`；subtask `wait` → `STARVED`。

### 4.5 Buffer（`env["storage"][key]`）


| 代码 state  | 映射状态      | reason                   |
| --------- | --------- | ------------------------ |
| `empty`   | `EMPTY`   | occupancy=0              |
| `partial` | `PARTIAL` | 0 < occupancy < capacity |
| `full`    | `FULL`    | occupancy = capacity     |


Buffer 的 `BLOCKED`/`STARVED` 在窗口聚合阶段由上下游 machine 状态推导，第一版原始日志只记 occupancy 变化。

### 4.6 Material


| 条件                     | shortage_flag | 说明                              |
| ---------------------- | ------------- | ------------------------------- |
| 下道工序所需 submaterial 未就位 | `1`           | 从 `task_record` + `material` 判断 |
| 正常                     | `0`           | —                               |

### 5.2 disturbance_log.csv

**粒度**：episode 开始写 1 行 **配置扰动**（L0/L1）；每个 L2 故障/离岗/物流/缺料事件写 **start 行 + end 行**（同一 `disturbance_id`）。`quality_hold` 在 episode 开始写 **一行**（窗口 `start`/`end` 都已填，id 为 `qc_hold_{i}`）。`--disturbance_dim none` 时仅表头。无 `episode_id` 列（由目录 `episode_XX/` 隐含）。


| 字段                     | 类型        | 取值来源                         | 说明                                                                                                      |
| ---------------------- | --------- | ---------------------------- | ------------------------------------------------------------------------------------------------------- |
| `run_id`               | str       |                              |                                                                                                         |
| `env_id`               | int       |                              |                                                                                                         |
| `disturbance_id`       | str       | 注入器                          | **不是 int**。配置行 `{dim}_cfg`（如 `machine_cfg`）；L2 故障为 `{dim}_event_{n}`；质检为 `qc_hold_{i}`                 |
| `disturbance_type`     | str       | 注入器                          | 配置行 `{dim}_config`；L2：`machine_failure` / `human_unavailable` / `transport_delay` / `material_shortage` / `quality_hold`；看门狗误杀/真卡死为 `deadlock_reset`（见 [`05.龙门架死锁&WIP槽位修复.md`](./05.龙门架死锁&WIP槽位修复.md)） |
| `target_resource_id`   | str       |                              | 配置行 = `episode`；L2 = 工位级 ID，如 `...CuttingMachine_ws0` / `gantry_0` / `robot_0` / `human_0`                          |
| `target_resource_type` | str       |                              | 配置行 = dim（`machine`）；L2 同 dim（物流 L2 的 type 仍可能是 `logistics`，`target_resource_id` 为 `gantry_*` 或 `robot_*`）          |
| `start_time_step`      | int       | 注入时刻                         | 配置行 = `0`；L2 start/end 两行同一 start                                                                       |
| `end_time_step`        | int | 空   | 恢复时刻                         | 故障类：**start 行留空**，end 行填结束步；`quality_hold`：**一行内同时填窗口起止** |
| `start_logic_time_s`   | float     | `start_time_step × logic_dt` |                                                                                                         |
| `end_logic_time_s`     | float | 空 |                              | 与 `end_time_step` 同步                                                                                    |
| `severity`             | 空         | 未写入                          | 列存在但当前为空；强度见 `episode_config.disturbance_intensity`                                                     |
| `parameter_before`     | str       |                              | 配置行 `nominal`；L2 start=`nominal`，end=`disturbed`                                                        |
| `parameter_after`      | str       |                              | 配置行 = `applied` 的 JSON（含 `event_schedule`）；L2 start=`disturbed`，end=`restored`                          |
| `notes`                | str       |                              | 配置行 `primary_dimension=...`；L2 `event start/end at step ...`                                            |


**L2 日程（每个 episode 重采样）**：默认 `event_schedule_mode=resample_per_episode`。用 `(seed, env_id, episode_id)` 抽互不重叠事件。I=1.0 / 2.0 / 3.0 条数 **2 / 2–3 / 3–4**（`material` L2 条数见 [`02.瓶颈维度&环境扰动.md`](./02.瓶颈维度&环境扰动.md) §3.5）。起点约 400–8000；时长 `clip(U(0.7,1.3)×基准×I, 600, 上限)`，上限约 900 / 1300 / 1400 步（始终 `< stall 5000`）。基准：machine 700、human 800、logistics 650、material 800。间隔 ≥360。目标池：`machine` 为切管/坡口/焊机/工作台；`human` 为 `human_*`；`logistics` 为当前 `gantry_*` **和** `agv_*`（现行代码每局至少冻一台 AGV）；`material` 为 `product_00_flange` / `product_00_elbow`（**不藏管坯**）。`material` 另有开局 L1 波：每局抽法兰或弯头，I=1.0 藏 6–7 件（留 3）、约 1400–2200 步，到期放回；**reset 不再永久跳过放料**。一次只激活一条；目标当前无法下手则等到可执行；等待超过 `max(2×duration, 500)` 则跳过。计划队列写在该 episode 的配置行 `parameter_after.event_schedule` 以及 `episode_config.disturbance_applied`。调试可把 mode 设为 `fixed` 并预填 `event_schedule`。已落地 77 局生产包仍是下限 6 分钟、无 AGV 保证的旧采样。

**`machine` 额外项**：L0 从 I=1.0 起关掉工作台 ws1 **和** 旋转焊 ws1；L1 `tool_wear_per_1k_steps=15I`（加工目标随 `time_step` 变长）；L2 另抽 1–4 个 `quality_hold` 窗口（不占故障槽位）。窗口内若焊/组对工序刚要完工，机台保持 `PROCESSING` 再等 `hold_steps` 才放行。

离线 Stage-C 把已完成（以及 `--follow` 时截到当前末端）的 L2 区间写进节点特征 `disturbance_active_s`，当作**环境上下文**。L2 **不**并入 `bottleneck_event.csv`，也**不**驱动 `will_bottleneck` / `root_cause_reason`。`quality_hold` 仍排除在 L2 特征集合之外。

### 5.3 resource_event_log.jsonl

**粒度**：每个资源**状态或 subtask 变化**一行（事件驱动）。Collector 每步对比 `(raw_state, norm_state, subtask_name, reason)` 签名。

**公共字段**（每行 JSON 对象均包含）：


| 字段                | 类型         | 取值来源                                               | 说明                              |
| ----------------- | ---------- | -------------------------------------------------- | ------------------------------- |
| `run_id`          | str        |                                                    |                                 |
| `env_id`          | int        |                                                    |                                 |
| `episode_id`      | int        |                                                    |                                 |
| `time_step`       | int        | `env["time_step"]`                                 | 变化发生后的步                         |

## 7. 离线派生表（不在仿真内写）

脚本：`tools/bn_agg`（`python3 -m bn_agg`）。默认 `--window_sizes 30,60`、`--horizon 180`、`--score_threshold 0.55`、`--min_event_windows 1`。  
输出：`<run_dir>/derived/episode_XX/env_YY/`。

### 7.1 window_feature_table.csv

**粒度**：每个 `(window_size_s, window_index, resource_id)` 一行。同一文件内已含 `bottleneck_score_s` 与窗口内归一化列。


| 字段                                                                                                           | 说明                         |
| ------------------------------------------------------------------------------------------------------------ | -------------------------- |
| `run_id`, `env_id`                                                                                           |                            |
| `window_index`                                                                                               | 从 0                        |
| `window_start_s`, `window_end_s`, `window_size_s`                                                            | 逻辑秒                        |
| `resource_id`, `resource_type`                                                                               | 与 §3 对齐；扰动 ID 需解析到 `*_ws0` |
| `queue_length_s`, `avg_waiting_time_s`, `occupancy_ratio_s`, `queue_growth_rate_s`                           | Queue                      |
| `active_pct_s`, `current_active_duration_s`, `blocked_time_s`, `starved_time_s`, `stop_time_s`, `unavailable_pct_s`, `inter_departure_var_s` | Process；`STOP` 为宕机/未启用工位 |
| `upstream_blocked_ratio_s`, `downstream_starved_ratio_s` | 工艺邻接（非全局） |
| `route_delay_s`, `inbound_wait_s`, `material_shortage_propagation_s`, `affiliated_buffer_occ_s`, `tb_minus_ts_s`, `disturbance_active_s`, `is_turning_point`, `is_momentary_bn` | 节点局部 system / 检测器 |
| `bottleneck_score_s`                                                                                         | 见下式                        |
| `norm_queue_length_s`, `norm_avg_waiting_time_s`, `norm_current_active_duration_s`                           | 同一窗口内 min-max              |


```text
stall_pct = (blocked_time_s + starved_time_s) / window

bottleneck_score_s =
    0.15 * norm(queue_length_s)          # 工位 WIP，仓库库存不进此项
  + 0.10 * norm(avg_waiting_time_s)
  + 0.20 * stall_pct
  + 0.10 * active_pct_s
  + 0.05 * norm(current_active_duration_s)
  + 0.10 * upstream_blocked_ratio_s
  + 0.10 * downstream_starved_ratio_s
  + 0.00 * unavailable_pct_s             # STOP 是扰动/配置，只进 X
```

现行无监督占用 y 是 `factory_bn.remain.ops_hot_mask`（过程启发式，**不用**分数）。有监督才用 `node_hot_mask`（过程规则 ∪ `score≥0.55` ∪ TPM）。最短热段 8 分钟。仓库库存、日常 stall、窗内峰值、注入 L2 本身不当事件。`queue_enter` 等待挂到下游 `output_buffer_id`（机器）对应的 `*_ws0`。`inbound_wait_s` 含未完成运次，并摊到对应库区里本窗正在 STARVED/WAITING 的工位。模型主输出与评测见 [`模型评估指标.md`](./模型评估指标.md)。
